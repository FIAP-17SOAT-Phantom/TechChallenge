1. Visao geral da Fase 2

A Fase 1 entregou um sistema que ja gerencia clientes, veiculos, pecas e ordens de servico. A Fase 2 nao reescreve esse sistema: ela o evolui para ser mais organizado, testavel e preparado para escalar. O objetivo e transformar "um programa que funciona na minha maquina" em "um sistema que roda de forma confiavel em um cluster, com deploy automatizado".

Os quatro grandes temas da fase sao:

TemaO que significa na pratica
Qualidade de codigoClean Code e Clean Architecture: separar o codigo em camadas com responsabilidades claras, e cobrir os fluxos criticos com testes automatizados.
ConteinerizacaoEmpacotar a aplicacao em imagens Docker, para que rode igual em qualquer lugar.
OrquestracaoUsar Kubernetes para rodar varias copias da aplicacao, com escalonamento automatico (HPA) conforme a carga.
AutomacaoTerraform (criar a infraestrutura via codigo) e CI/CD (build, teste e deploy automaticos a cada push).

3. A arquitetura da aplicacao (Clean Architecture)

A solucao esta dividida em projetos .NET, cada um com uma responsabilidade. A regra de ouro: o dominio nao conhece ninguem; todos conhecem o dominio.

4. Fluxo completo da Ordem de Servico

Toda a logica gira em torno da Ordem de Servico (OS). Ela e uma maquina de estados: so pode passar de um status para outro em uma ordem valida. A entidade OrdemDeServico protege essas regras.

StatusSignificaComo avanca
RecebidaOS acabou de ser abertaMecanico inicia o diagnostico
EmDiagnosticoMecanico avaliando o veiculoRegistra o diagnostico e os itens
AguardandoAprovacaoOrcamento enviado ao clienteCliente aprova (direto ou via webhook externo)
EmExecucaoServicos sendo executados; estoque reservadoTodos os servicos executados e OS finalizada
FinalizadaServico concluidoVeiculo entregue ao cliente
EntregueEncerramento do ciclo-

Existe ainda o status Cancelada, permitido a partir de estados nao-finais.

Ponto-chave da arquitetura: a transicao de status esta no metodo privado AlterarStatus da entidade, que dispara um evento de dominio (OrdemDeServicoStatusAlteradoEvent) toda vez que o status muda. Esse evento e o gatilho da notificacao por e-mail (secao 6).

5. As APIs obrigatorias da Fase 2 (uma a uma)

5.1. Abertura de OS

POST /api/ordens-de-servico/abertura

Recebe em um unico request os dados de cliente, veiculo, servicos e pecas, e devolve o identificador unico da OS. O passo a passo interno:

  1. O AbrirOrdemDeServicoHandler valida a estrutura do pedido.
  2. Normaliza CPF, e-mail e placa (Value Objects garantem o formato).
  3. Resolve ou cria o Cliente e o Veiculo.
  4. Valida se os servicos e pecas existem no catalogo.
  5. Gera o numero da OS por uma sequence atomica do PostgreSQL (OS-0001, OS-0002...), evitando colisao quando varias instancias abrem OS ao mesmo tempo.
  6. Persiste tudo em uma transacao e retorna 201 Created com o id.

5.2. Consulta de status

GET /api/ordens-de-servico/{id}/status

Retorna o status atual da OS (Recebida, EmDiagnostico, AguardandoAprovacao, EmExecucao, Finalizada, Entregue) junto com as datas relevantes. Implementado pelo ConsultarStatusOrdemDeServicoHandler.

5.3. Aprovacao de orcamento (notificacao externa)

POST /api/webhooks/orcamentos/{id}/resposta

Este e o endpoint que recebe a aprovacao ou recusa vinda de um sistema externo. Ele e cuidadosamente protegido:

  • Assinatura HMAC: o chamador envia o header X-Webhook-Signature; o servidor recalcula a assinatura com um segredo compartilhado e compara. Sem isso, qualquer um poderia aprovar orcamentos.
  • Tolerancia de tempo: rejeita requisicoes com timestamp muito antigo (evita "replay").
  • Idempotencia: cada evento externo tem um id; se chegar duas vezes, a segunda e ignorada (retorna "repetido"). Isso evita reservar estoque em dobro.

Ao aprovar, a OS vai para EmExecucao e o estoque das pecas e reservado em uma transacao serializable.

5.4. Listagem de OS (com a regra da fase)

GET /api/ordens-de-servico

A listagem obedece exatamente a regra pedida no enunciado:

  • Ordenacao por prioridade de status: Em Execucao > Aguardando Aprovacao > Em Diagnostico > Recebida.
  • Mais antigas primeiro dentro de cada status (por data de abertura).
  • Exclusao logica das OS Finalizadas e Entregues: elas somem da listagem, mas continuam no banco (nada e deletado) e seguem acessiveis por GET /api/ordens-de-servico/{id}.

Essa regra fica na consulta do repositorio (GetAllAsync em OrdemDeServicoRepository), usando um filtro Where que exclui os status finais e um OrderBy com a prioridade:

.Where(os => os.Status == EmExecucao
          || os.Status == AguardandoAprovacao
          || os.Status == EmDiagnostico
          || os.Status == Recebida)
.OrderByDescending(os => os.Status == EmExecucao)
.ThenByDescending(os => os.Status == AguardandoAprovacao)
.ThenByDescending(os => os.Status == EmDiagnostico)
.ThenBy(os => os.DataAbertura)   // mais antigas primeiro

5.5. Atualizacao de status via e-mail

Nao e um endpoint que voce chama: e automatico. Cada mudanca de status gera um e-mail para o cliente. O "como" esta na proxima secao.

6. Notificacao de status por e-mail (Outbox + Worker)

Enviar e-mail direto no meio de uma transacao e arriscado: se o e-mail falha, voce nao quer desfazer a mudanca de status; e se a transacao falha depois do e-mail, voce ja mandou uma notificacao errada. A solucao e o padrao Outbox transacional.

Passo a passo

  1. A OS muda de status e dispara um evento de dominio.
  2. Esse evento e gravado como uma linha na tabela OutboxMessages, na mesma transacao do dado. Ou grava os dois, ou nenhum.
  3. O Worker (processo separado) fica fazendo polling dessa tabela.
  4. Para cada mensagem, o OutboxProcessor monta o e-mail (assunto e corpo conforme o status) e envia pelo IEmailSender.
  5. Se o envio falha, ele tenta de novo com backoff exponencial, ate um limite de tentativas.
Importante sobre o envio real: existem dois provedores de e-mail. O padrao e Log, que apenas escreve no log (nao envia de verdade) — otimo para desenvolvimento. Para enviar e-mails reais, configure Email:Provider = Resend e Email:ResendApiKey (uma conta no servico Resend). O destinatario e sempre o e-mail do cliente cadastrado na OS.

API e Worker nao conversam por HTTP: eles se comunicam apenas atraves do banco de dados (a tabela do outbox). Isso desacopla os dois e permite escalar cada um separadamente.

7. Conteinerizacao (Docker e docker-compose)

7.1. Dockerfile

Cada processo (API e Worker) tem seu Dockerfile, usando multi-stage build:

  • Estagio build: usa a imagem do SDK .NET 8, restaura pacotes, compila e publica.
  • Estagio final: usa a imagem menor (apenas runtime), copia so o resultado publicado e roda como usuario nao-root (seguranca).

O resultado e uma imagem enxuta e segura. A API expoe a porta 8080 e tem um healthcheck em /health/ready.

7.2. docker-compose.yml

Para desenvolvimento local, o docker-compose.yml sobe tres servicos de uma vez:

ServicoO que e
dbPostgreSQL 16 com volume persistente e healthcheck (pg_isready).
apiA API; so sobe depois que o banco esta saudavel. Aplica migrations e semeia o admin no startup.
workerO processador do outbox; sobe depois de banco e API.

As variaveis sensiveis (senhas, JWT) vem do arquivo .env (criado a partir de .env.example), nunca versionadas.

docker compose up --build
# API:     http://localhost:8080
# Swagger: http://localhost:8080/swagger

8. Orquestracao com Kubernetes (manifestos)

Os manifestos ficam em k8s/, organizados com Kustomize (uma forma de ter uma "base" comum e "overlays" por ambiente). Cada arquivo YAML descreve um recurso do cluster.

ArquivoRecursoPara que serve
namespace.yamlNamespaceIsola todos os recursos da oficina em um espaco proprio.
configmap.yamlConfigMapConfiguracoes nao sensiveis (ambiente, host do banco, intervalos do outbox).
secret.example.yamlSecret (modelo)Modelo para os segredos (senha do banco, JWT, webhook). O arquivo real nunca e versionado.
deployment.yamlDeployment (API)Roda a API com 2 replicas, probes de saude, init container que espera as migrations e seguranca reforcada (nao-root, filesystem somente-leitura).
worker-deployment.yamlDeployment (Worker)Roda o processador do outbox.
service.yamlServiceDa um endereco interno estavel para a API dentro do cluster.
hpa.yamlHorizontalPodAutoscalerEscala a API de 2 a 6 replicas conforme CPU (70%) e memoria (80%). E a "escalabilidade dinamica" da fase.
pdb.yamlPodDisruptionBudgetGarante um minimo de pods disponiveis durante manutencoes.
migration-job.yamlJobAplica o schema do banco (migrations) e semeia o admin antes da API subir.
service-account.yamlServiceAccountIdentidade dos pods no cluster (com permissoes minimas).

O overlay k8s/overlays/local acrescenta um PostgreSQL rodando dentro do cluster (StatefulSet) e aponta para imagens locais, para testes sem nuvem.

kubectl apply -k k8s/overlays/local
kubectl -n oficina-mecanica get pods
kubectl -n oficina-mecanica get hpa
Como o HPA demonstra escalabilidade: ao gerar carga nos endpoints, o uso de CPU sobe; o HPA percebe e cria novos pods automaticamente (ate 6). Quando a carga cai, ele remove os pods extras. E exatamente o cenario de "horario de pico" descrito no enunciado.

9. Infraestrutura como Codigo (Terraform)

Em vez de criar o cluster e o banco "na mao", o Terraform descreve tudo em arquivos na pasta infra/. Rodar terraform apply cria toda a infraestrutura; terraform destroy remove. E repetivel e versionavel.

ArquivoPara que serve
versions.tfDeclara a versao do Terraform e os providers usados (kind, kubernetes, helm, null).
variables.tfDefine as "perguntas" configuraveis: nome do cluster, nome do banco, senhas, segredos. Com valores padrao e marcadas como sensiveis quando necessario.
main.tfO coracao: cria o cluster Kubernetes (kind), o namespace, o banco PostgreSQL (via Helm) e o Secret da aplicacao. Opcionalmente aplica os manifestos.
outputs.tfMostra informacoes uteis apos o apply: nome do cluster, contexto kubectl, URL da API, endereco do banco.
terraform.tfvars.exampleModelo de valores reais. Voce copia para terraform.tfvars e preenche as senhas (esse arquivo nao e versionado).
infra/README.mdDocumenta todos os recursos criados, as variaveis e o passo a passo (local e adaptacao para AWS EKS + RDS).

Recursos que o Terraform cria

  • kind_cluster.oficina — cluster Kubernetes local (1 control-plane + 1 worker), com a porta 30080 exposta no host.
  • kubernetes_namespace.oficina — o namespace da aplicacao.
  • helm_release.postgres — o banco PostgreSQL 16 dentro do cluster (pode ser desligado para usar banco gerenciado).
  • kubernetes_secret.oficina — o Secret oficina-secrets com as senhas e segredos.
  • null_resource.kustomize — opcionalmente aplica os manifestos K8s ao final.
cd infra
cp terraform.tfvars.example terraform.tfvars   # preencha as senhas
terraform init     # baixa os providers
terraform plan      # mostra o que sera criado
terraform apply     # cria o cluster + banco + secret
Local vs. nuvem: o padrao usa kind (Kubernetes rodando em Docker) por ser simples de demonstrar. O infra/README.md explica como trocar para AWS: o modulo EKS no lugar do kind, e o modulo RDS no lugar do PostgreSQL via Helm. O resto dos manifestos continua igual, porque sao agnosticos ao provedor.

10. CI/CD (GitHub Actions)

Sao dois pipelines, cada um com um papel. Ambos ficam em .github/workflows/.

10.1. CI — ci.yml (qualidade)

Dispara a cada push ou pull request na branch main. Tem tres trabalhos:

  1. Build + testes unitarios + cobertura: compila, roda os 141 testes unitarios e gera relatorio de cobertura.
  2. Testes de integracao: sobe um PostgreSQL real com Testcontainers e roda os testes de ponta a ponta.
  3. Scan de vulnerabilidades: checa se ha pacotes NuGet com falhas conhecidas.

Existe tambem o build.yml, que faz a analise de qualidade no SonarQube Cloud.

10.2. CD — cd.yml (entrega)

Dispara em push na main ou em tags v*. E a esteira completa ate o deploy:

  1. Build e testes (gate): so segue se tudo passar.
  2. Build e push das imagens Docker (API e Worker) para o GitHub Container Registry (GHCR).
  3. Terraform apply: provisiona o cluster kind + PostgreSQL + Secret.
  4. Deploy: carrega as imagens no cluster, aplica os manifestos YAML e roda a Job de migration do banco.
  5. Validacao: espera o rollout da API terminar e exibe o estado dos pods e do HPA.
push na main
  -> CI (ci.yml): build + testes + scan
  -> CD (cd.yml): build/push imagens -> terraform apply
                   -> kubectl apply -k -> migration -> rollout

12. Como rodar tudo (roteiro pratico)

Opcao A — Local, o mais rapido

cp .env.example .env     # preencha JWT_SECRET, ADMIN_PASSWORD, POSTGRES_PASSWORD...
docker compose up --build
# abra http://localhost:8080/swagger

Opcao B — Kubernetes

cp k8s/base/secret.example.yaml k8s/base/secret.yaml   # preencha os segredos
kubectl apply -k k8s/overlays/local
kubectl -n oficina-mecanica rollout status deployment/oficina-api

Opcao C — Terraform (infra do zero)

cd infra
cp terraform.tfvars.example terraform.tfvars    # preencha as senhas
terraform init && terraform apply

Primeiros passos na API

  1. Faca login em POST /api/auth/login com o admin semeado.
  2. Use o token no botao "Authorize" do Swagger.
  3. Cadastre Cliente, Veiculo, Servico e Peca.
  4. Abra uma OS em POST /api/ordens-de-servico/abertura.
  5. Acompanhe o status em GET /api/ordens-de-servico/{id}/status.
  6. Liste as OS em GET /api/ordens-de-servico e veja a ordenacao por prioridade.
Resumo mental: o codigo (Clean Architecture) vira uma imagem (Docker), que roda em copias gerenciadas pelo Kubernetes (com HPA para escalar), sobre uma infraestrutura criada por Terraform, tudo publicado automaticamente pelo CI/CD. Cada peca resolve um dos objetivos da Fase 2.
